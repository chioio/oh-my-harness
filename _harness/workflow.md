# 默认工作流

本项目中的 agent 默认按照“分析指示 → 查阅上下文/资料 → 给出建议结论 → 执行最小必要动作”的方式推进。

## 通用执行流程

1. 读取 `AGENTS.md`
2. 根据任务类型路由到 `_harness/` 内最相关的文件
3. 形成当前任务判断
4. 如果属于决策性质改动，先向用户确认
5. 如果属于可直接执行的改动，则进行最小必要实现
6. 完成后总结变化，并在需要时更新 memory

## harness 演化工作流

适用于：

- 调整规则
- 调整 routing
- 调整 workflow
- 调整 memory / GC 机制
- 优化结构

建议步骤：

1. 明确用户意图
2. 读取 `_harness/readme.md`、`_harness/rules.md`、`_harness/workflow.md`
3. 判断是局部改进还是结构性演化
4. 若涉及决策边界，先确认
5. 小步实施
6. 将稳定结论沉淀到 `_harness/memory/project.md`

## kit 演化工作流

适用于：

- 调整 setup 输出内容
- 调整目标项目中的私有 / 共享边界
- 改进 kit 结构
- 增强 kit 的系统完整性

建议步骤：

1. 先确认当前变更针对的是仓库自用 harness，还是 `kit/` 输出系统
2. 若涉及 `kit/` 职责边界、输出哲学或 setup 模型，视为决策性质变更
3. 保持 `kit/` 输出内容最小可用且可持续演化
4. 让 setup 输出逐步接近“kit 即系统”
5. 验证落地到项目后的解析链路是否完整

## setup 设计 / 落地工作流

适用于：

- 修改 `setup` 命令
- 定义 setup 后应写入目标项目的内容
- 改进目标项目中的 `AGENTS.md` / `AGENTS.local.md` / `_harness/` 行为

建议步骤：

1. 明确 setup 目标
2. 明确当前采用默认私有模式还是可提交 harness 模式
3. 明确哪些内容共享，哪些内容本地私有
4. 确保目标项目中的 `AGENTS.md` 可提交远端
5. 确保默认模式下 `AGENTS.local.md` 与 `_harness/` 被忽略
6. 确保可提交模式下 `_harness/` 不再被忽略，且可不生成 `AGENTS.local.md`
7. 确保 `AGENTS.md` 在存在 `AGENTS.local.md` 时会继续解析它；否则在存在 `_harness/` 时继续解析共享 harness
8. 确保 setup 后存在补充占位，以驱动 agent 完成项目内补充
9. 验证 setup 结果是否符合预期

## 外部工具集成工作流

适用于：

- 引入新的 harness engineering 工具
- 比较外部项目做法
- 接入技能、审计或辅助能力

建议步骤：

1. 先做调研与比较
2. 明确该工具是否真正改善当前 harness 系统
3. 优先做兼容和适配，而不是推倒重来
4. 若引入会改变系统定位或结构哲学，先确认
5. 集成后更新相关文档与 memory

## 数据 / 表格汇总工作流

适用于：

- 汇总结构化信息
- 生成表格
- 整理比较结果

建议步骤：

1. 明确输入来源与输出格式
2. 选择最小必要上下文
3. 保持结构化、可检查、可复用
4. 如结果将长期复用，可沉淀为 memory 或工具能力

## memory 更新流程

### 写入长期 memory 的情况

- 用户明确表达稳定偏好
- harness 结构或边界形成长期决策
- setup 落地规则得到确认
- 某项原则在多次任务中反复出现且稳定有效

### 写入短期 memory 的情况

- 当前任务的上下文
- 尚待验证的假设
- 中间分析结论
- 交接前需要保留的信息

### GC 原则

- 临时信息不长期保留
- 重复内容要压缩
- 失效内容应删除
- 优先保持高信号、低噪音
